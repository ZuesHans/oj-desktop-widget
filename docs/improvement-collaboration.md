### T05：可选密码加密备份

入口：[`backup_service.dart`](../lib/services/backup_service.dart)、[`automatic_backup_service.dart`](../lib/services/automatic_backup_service.dart)、[`data_recovery_service.dart`](../lib/services/data_recovery_service.dart)、设置与导入导出界面。

第一阶段针对手动便携备份提供可选加密；自动备份和导入前安全备份是否加密、如何无人值守取密钥，必须单独说明，不能宣称所有备份已加密。现有 `crypto` 依赖用于哈希，不等于已经具备 AES-GCM 或 scrypt。

实施范围：

- 在现有备份 payload 外包一层带 magic、格式版本、KDF 参数、随机 salt、随机 nonce、密文和认证标签的容器。
- 采用经过维护的密码库实现 scrypt + AES-GCM；参数在目标 Windows 设备上测量后确定。限制导入容器允许的内存/计算参数，避免恶意文件消耗过量资源。
- 每次导出使用新的 salt 和 nonce；将格式版本及影响解密的头部信息纳入认证。密码不写配置、日志、剪贴板或备份文件。
- 导入根据内容识别旧明文 JSON、新加密容器及现有核心备份；先解密、校验并完整解析，再进入现有安全备份与替换事务。
- 避免在磁盘留下明文临时文件。加密导出不能沿用旧路径额外生成含账号统计的明文 CSV 而不告知用户；默认关闭该旁路导出。

验收：

- [ ] 旧明文备份仍可恢复；同一数据的两次加密输出不同且都能正确解密。
- [ ] 错误密码、篡改内容、截断文件、未知版本均不改写现有数据；密码取消也不会开始替换。
- [ ] 密码输入有确认和“忘记密码无法恢复”的明确提示；处理大备份时界面可响应。
- [ ] 明确列出手动备份、自动备份、安全备份各自的加密状态；不会误导用户把未加密文件当作密文。

### T06：刷新限流、退避与下次时间

入口：[`refresh_service.dart`](../lib/services/refresh_service.dart)、[`teammate_service.dart`](../lib/services/teammate_service.dart)、[`module_http_client.dart`](../lib/services/module_http_client.dart)、[`http_client.dart`](../lib/core/http_client.dart)、[`oj_tile.dart`](../lib/ui/dashboard/oj_tile.dart)。

实施范围：

- 在实际 HTTP 请求边界按 `Uri.host` 排队；同一个 provider 可能访问不同域名，不应只按 OJ ID 建锁。本人账号、队友和后续历史导入共享同一主机的限制。
- 建议从每主机最多 2 个并发请求开始，形成可调整的集中配置。信号量覆盖响应流消费或关闭，避免只限制收到响应头之前的瞬间。
- 对 429 与可恢复的 5xx 使用有上限的指数退避和抖动；解析 `Retry-After` 的秒数与 HTTP 日期。默认不重试认证失败、无效账号、解析失败等确定性错误。
- 明确哪些请求可安全重放；只读 GraphQL POST 等请求也要显式分类，不能无条件重试所有 POST。
- 统一重试次数、总时间预算与取消：不能继续套用外层 18 秒超时，让内部退避超时后仍在后台请求。关闭模块、退出和取消导入应终止排队与等待。
- 区分常规自动刷新时间与主机冷却恢复时间；冷却期间手动刷新不应制造新一轮风暴，界面显示时间与原因。

验收：

- [ ] 多账号同主机时不超过设定并发，不同主机可并行；本人和队友请求不会绕过共同限制。
- [ ] 模拟 429、503 和 `Retry-After`，验证尝试次数、时间预算和下一次可刷新时间；等待过程可取消。
- [ ] 某一平台持续失败不阻塞其他平台；最后成功数据和失败原因仍能展示。
- [ ] 用注入的时钟、随机源和等待器验证调度，无需在测试里真实等待长退避时间。

### T07：可选间隔复习调度

入口：[`training_service.dart`](../lib/services/training_service.dart)、[`training.dart`](../lib/models/training.dart)、[`problem_record.dart`](../lib/models/problem_record.dart)、[`oj_controller.dart`](../lib/services/oj_controller.dart)、训练页和首页训练安排。

**需要先处理的现状**：模型和 SQLite 保留了 `reviewStage`、`nextReviewAt`，但 `normalizeLegacyProblems` 会清除旧复习状态与日期，`normalizeTrainingData` 会删除 `reviewDue` 任务；`_applyResult` 也会清除复习日期。这与此前改为手动安排训练的行为一致。新功能必须把旧数据迁移与新数据正常加载区分开，否则日期会在重启或导入后被清掉。

建议首版作为可选功能，手动安排继续可用。以下规则属于设计提案，认领者需要在实施前确认并记录最终规则：

| 场景 | 建议行为 |
| --- | --- |
| 独立 AC（`assistance = none`） | 从阶段 0 开始，依次安排 1 / 3 / 7 / 21 天后的复习；每个间隔相对本次完成时间计算 |
| 提示后 AC | 不提升熟练阶段，建议次日再复习 |
| 看题解后 AC，或 WA/TLE/RE/放弃 | 重置阶段，建议次日再复习 |
| 跳过、取消、归档 | 不当作成功复习；归档题退出到期队列 |
| 完成最后一个阶段 | 标为已掌握并停止自动排期，保留手动重置入口 |
| 已逾期 | 继续计入今日待复习，不因错过日期而消失 |

日边界沿用 [`core/time.dart`](../lib/core/time.dart) 的本地 04:00 训练日规则。到期判断、首页计数和待办列表必须使用同一规则。到期队列可以从日期派生，也可以物化为任务，但需明确唯一性，避免同时生成手动与自动的重复待办。

验收：

- [ ] 首次安排、阶段推进、失败重排、辅助完成、归档和最后阶段完成均有确定行为。
- [ ] 首页显示“今日待复习 N 题”，可直接进入题目或开始训练；完成后立即更新下一次日期与计数。
- [ ] 过期题只出现一次；手动改期、关闭调度和重新开启后的行为有说明。
- [ ] 新版日期和任务经重启、备份导入、同步以及 companion 编辑后保持一致；旧数据迁移不会循环执行。
- [ ] 覆盖 03:59 / 04:00、月末和年末；任何数据结构变更同时更新 Flutter、SQLite 和原生 companion 契约。

### T08：首日历史导入

入口：现有 [`providers/`](../lib/providers/)、[`heatmap_service.dart`](../lib/services/heatmap_service.dart)、[`daily_summary_service.dart`](../lib/services/daily_summary_service.dart)、[`solved_snapshot.dart`](../lib/models/solved_snapshot.dart)。

分阶段交付：先定义提交记录与 CSV 契约，支持预览和去重；再接入 CF 的分页历史提交；洛谷和 LeetCode 在核实公开接口、分页和可用历史范围后分别接入。不能假定各平台都能匿名读取完整历史，也不把采集 Cookie 作为默认方案。

实施范围：

- CSV 至少包含平台、账号、题目标识、提交时间及时区、判题结果；在线来源还应保存提交 ID，并说明每列格式。
- 先预览可导入、重复、无效和超出范围的数量；允许选择最近 N 条或时间范围，展示实际覆盖范围与抓取截断原因。
- 提交去重与“每日唯一 AC 题目”去重分开定义；同一道题多次 AC 不应被误计为多道新通过题。
- 历史提交是独立数据来源，不直接伪造累计通过数快照。最近 N 条不能证明完整历史总数，也不能绕过现有通过数下降保护。
- 复用 `exact / estimated / unknown` 的准确度表达或建立明确的新来源字段；在线导入复用 T06 的调度与取消。

验收：

- [ ] 同一文件或同一批提交重复导入不重复计数；有错误行时可定位，确认前不改写数据。
- [ ] 首次导入后热力图和趋势出现历史数据，且不会篡改当前总通过数。
- [ ] 部分历史、账号切换、重复题目、跨训练日时间、分页失败和取消都有可解释结果。
- [ ] 导入结果能经备份导出恢复；大历史量不会被现有 6000 条快照保留规则意外截断。

### T09：目标、周报和比赛提醒

三个子任务分别交付，避免把目标、图片导出与系统通知耦合为一个大 PR。

**T09-A 每日目标**：在配置中加入可关闭的题数/专注时长目标。训练日仍按 04:00 划分；实施前确定“题数”指完成训练题、独立 AC 题，还是 OJ 当日唯一通过题，不能把三者混算。首页显示实际值、目标值与进度；0 表示关闭的语义要明确，旧配置保持可读。

**T09-B 周报卡**：先做手动生成与保存 PNG。约定一周起止日期、计数口径和数据来源；展示有效训练时长、完成题数、平台分布及主要错误类型等有现有数据支撑的指标。导出默认隐藏账号、笔记与复盘正文，由用户自行分享；周末自动生成属于后续可选行为。

**T09-C 比赛提醒**：先获取 CF / AtCoder 即将开始的比赛，并支持 `.ics` 文件导出，再接入可关闭的本地通知。`.ics` 导出文件本身不等于持续更新的订阅；若提供订阅，需说明可长期访问的订阅地址、托管位置、刷新机制与离线行为，不以短暂运行的本地服务冒充常驻订阅。

验收：

- [ ] 目标保存后生效，跨训练日正确重置展示；目标数据与周报使用同一统计口径。
- [ ] 周报卡可保存，在 Windows 缩放与不同配色下无文字截断；只含用户同意公开的字段。
- [ ] 日历事件有稳定 UID、正确开始时间/时区与时长；重复导出不会制造重复事件。

## 4. 多人协作与交接方式

### 认领与分支

1. 在看板填负责人、状态和 Issue；在 Issue 或 PR 中限定本次子任务与验收项。
2. 第一组目前仍在本地分支，后续工作要从确实包含其改动的明确提交开始；接手前先看 `git status`。不要重置、清理或覆盖其他人的未提交内容，原有 `pubspec.lock` 镜像地址修改也需保留其归属。
3. 分支建议采用 `codex/repo-showcase`、`codex/diagnostics`、`codex/request-scheduling` 等与单一工作项对应的名称。
4. 完成后更新状态、勾选实际通过的验收项，附 PR、验证记录、兼容性影响和剩余问题。
